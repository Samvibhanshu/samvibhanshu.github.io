Mini-SQS

A message queue with Amazon SQS semantics, served over HTTP in SQS's own wire protocol, so the official AWS SDK works against it.

  • Systems (Java)
  • 2026
  • 39 tests

Why a queue is harder than a list

A consumer can crash halfway through a message. If receiving removed the message, it would be lost. So in SQS, receiving only hides it for the visibility timeout, and the consumer deletes it when finished. If the consumer dies, the message reappears and another consumer gets it. That gives at-least-once delivery: nothing is lost, but a message can be processed twice, so handlers must be idempotent.

Everything else follows from that one decision.

Problems and what the queue does about each

Queue problems and mechanisms
ProblemWhat this queue does
A slow consumer’s message reappears while it is still workingchangeVisibility(handle, ms) extends the timeout; 0 gives the message back at once
An old, slow consumer deletes a message that was since re-deliveredEach delivery gets a new receipt handle; only the latest one can delete, and stale handles return false
A “poison” message fails foreverAfter maxReceiveCount deliveries it moves to a dead-letter queue; redriveTo moves it back after the fix
A failing downstream gets hammered by instant retriesThe worker delays each retry by base × 2n−1, capped (exponential backoff)
Consumers poll an empty queue in a tight loopLong polling: receive(max, waitMs) sleeps until a message arrives or the wait ends; a send wakes it at once
Order matters (all events of one order, in sequence)FIFO queues: per message group, strict send order and one message in flight at a time; groups run in parallel
A producer retries a send after a timeoutFIFO deduplication: a repeated dedup id (or the same body, for content-based dedup) within 5 minutes is accepted but not stored again
Messages pile up foreverRetention: messages expire a set time after they were first sent, even if they moved to the DLQ

As a service: SQS's wire protocol

import boto3
sqs = boto3.client("sqs", endpoint_url="http://127.0.0.1:9324", region_name="us-east-1",
                   aws_access_key_id="local", aws_secret_access_key="local")
url = sqs.create_queue(QueueName="orders")["QueueUrl"]
sqs.send_message(QueueUrl=url, MessageBody='{"orderId": 42}')
for m in sqs.receive_message(QueueUrl=url, WaitTimeSeconds=20).get("Messages", []):
    sqs.delete_message(QueueUrl=url, ReceiptHandle=m["ReceiptHandle"])
  • The same protocol as SQS. The AWS SDKs send POST / with an X-Amz-Target: AmazonSQS.<Action> header and a JSON body; the server answers the same way. CI runs the AWS SDK for Python against it: 27 checks.
  • The details SDKs check. MD5 checksums of every body over its UTF-8 bytes (botocore refuses a response that does not match), and errors by name, so except sqs.exceptions.QueueDoesNotExist works.
  • SQS’s validation. Queue names, attribute ranges, FIFO needing a group and a deduplication id, allowed characters, batches of 1–10 entries that succeed or fail one by one.
  • Long polling holds a thread. At most 256 receives wait at once; past that a receive is answered immediately, so idle consumers cannot use up the server.
  • A bug found on the way: every response took about 40 ms until the server set TCP_NODELAY (the same bug as in order-service). Now about 2 ms.

How it is built

  • One lock per queue, and a Condition that long-polling receivers wait on. send and changeVisibility signal it.
  • Standard queue: a TreeSet ordered by “visible at” (ties broken by send order), so a receive takes the earliest visible message in O(log n). A message’s position depends on its visible-at time, so it is removed before that changes and re-inserted after. Forgetting that silently corrupts a sorted set; one of the planted bugs checks for it.
  • FIFO queue: one deque per group, in send order. Only the head of a group can be delivered, and an in-flight head blocks the rest of its group.
  • Two queues’ locks are never held together. Moving a message to the DLQ happens after the source queue’s lock is released, so there is no lock-order deadlock between a queue and its DLQ.
  • Time is injected (Clock). Tests use a manual clock, so “wait 30 seconds” takes no real time and every run is repeatable.

Using it

MessageQueue dlq = new MessageQueue("orders-dlq", QueueConfig.standard(30_000), Clock.SYSTEM);
MessageQueue q = new MessageQueue("orders", QueueConfig.standard(30_000).withDeadLetterQueue(dlq, 5), Clock.SYSTEM);

q.send("{\"orderId\":42}");
for (ReceivedMessage m : q.receive(10, 20_000)) {   // long poll up to 20 s
    process(m.body());
    q.delete(m.receiptHandle());                    // only after success
}

Do the tests catch real bugs? I planted 11 bugs one at a time, among them: old receipt handles still working, an off-by-one in the dead-letter count, changing a message’s visible-at time while it sits in the sorted set, retention restarting when a message moves to the DLQ, deduplication never expiring, backoff that does not grow, a send that does not wake long-polling receivers, and no round-robin between FIFO groups. All 11 were caught. For the HTTP layer, 6 more (checksums over the wrong bytes, no long-poll cap, a per-receive visibility timeout ignored, FIFO without a deduplication id accepted, WaitTimeSeconds ignored, one bad handle failing a whole batch): all 6 caught.
