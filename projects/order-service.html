Order service

An e-commerce order backend that never oversells, never charges twice, only makes legal state changes, and survives a crash.

  • Systems (Java)
  • 2026
  • 44 tests

The four things that go wrong

Real order systems fail in four ways, and this project is built around them:

  1. Overselling. 64 customers press “Buy” on the last 50 units at the same instant.
  2. Double charging. A payment request times out, the client retries, and the payment runs twice.
  3. Illegal states. An unpaid order ships, or a shipped order is cancelled and its stock is “returned”.
  4. Crashes. The server dies mid-request, and an order the customer was told about is gone after the restart.

There are no frameworks, no database and no dependencies: just the JDK, so every line is visible and explainable.

Every state change goes through one transition table. Cancelling a paid order sets refund=true.

Durability: the write-ahead log

  • Write, then apply. Each change is appended to the journal inside the same atomic step that applies it, and the step is not applied if the write fails. So the journal’s order is the real order of changes.
  • fsync before the answer, shared between requests (group commit). The fsync happens outside the lock: while one thread waits for the disk, others keep appending, and the next fsync covers all of them.
  • One record per change, keys included. An order and the idempotency key that created it are one record, so after a crash they are both there or both gone.
  • Recovery keeps the longest valid prefix and truncates the file before appending, otherwise the next recovery would stop at the old garbage and lose everything written after it.
  • Fail-stop. If a write or an fsync fails, the service refuses every later change with 503. After a failed fsync the OS may have dropped the data, so retrying could report success for writes that are gone.

Do the tests catch real bugs?

I planted 9 bugs in the business logic one at a time (unsorted lock order, a non-atomic idempotency check, a release that could run twice, …) and 6 in the durability layer (writes flushed only every 50 records, an idempotency key not stored with its order, a torn tail not cut, remembered errors not replayed, checksums not checked, a refused order keeping its stock). All 15 were caught.

A bug the new tests found in code that already existed: every HTTP response took about 40 ms. The JDK’s built-in server leaves Nagle’s algorithm on and writes the headers and the body separately, so the body waited for the client’s delayed ACK. With TCP_NODELAY the mean is about 2 ms, and a test guards it.
