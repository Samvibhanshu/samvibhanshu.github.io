Order service

An e-commerce order backend that never oversells, never charges twice and only makes legal state changes.

  • Systems (Java)
  • 2026
  • 30 tests

The three things that go wrong

Real order systems fail in three ways, and this project is built around them:

  1. Overselling. 64 customers press “Buy” on the last 50 units at the same instant.
  2. Double charging. A payment request times out, the client retries, and the payment runs twice.
  3. Illegal states. An unpaid order ships, or a shipped order is cancelled and its stock is “returned”.

There are no frameworks, no database and no dependencies: just the JDK, so every line is visible and explainable.

Every state change goes through one transition table. Cancelling a paid order sets refund=true.

Design decisions

  • Money is a long in paise or cents. Floating point cannot represent 0.1 exactly; totals use Math.multiplyExact and addExact, so overflow is an error, not a wrong bill.
  • Price before reserve. The total is computed before stock is reserved, so a pricing error can never leave units held by an order that does not exist.
  • Business errors are remembered, crashes are not. If an order failed as OUT_OF_STOCK, retrying the same key returns OUT_OF_STOCK again. An unexpected exception forgets the key so the client’s retry can actually run.
  • Immutable orders. Each change creates a new snapshot with version + 1, so readers never see a half-updated order.
  • Bounded input. Bodies are read up to 64 KB, JSON nesting is capped at 64 levels, and quantities and line counts are limited.

Do the tests catch real bugs?

I planted 9 bugs one at a time and re-ran the tests: unsorted lock order, a stock check that ignored the quantity, a non-atomic idempotency check, no fingerprint check, a fingerprint that depended on line order, a release that could run twice, no JSON nesting limit, cancel without releasing stock, and allowing a shipped order to be cancelled.

All 9 were caught. Two were missed at first, because the service happens to pass SKUs already sorted and never releases twice. InventoryTests now checks those guarantees on the inventory class directly.

What would change in production

Prototype versus production
HereIn production
In-memory maps and per-SKU locksA database conditional update (UPDATE stock SET available = available - ? WHERE sku = ? AND available >= ?) or a DynamoDB conditional write does the same check-and-subtract across many servers
Idempotency keys kept forever in memoryA table with a TTL, for example 24 hours
Event list in memoryAn outbox table written in the same transaction as the order, relayed to a queue
Reservations never expireUnpaid orders auto-cancel after N minutes to free stock

What it doesn’t do

  • It is in-memory only, so a restart loses everything.
  • Reservations never expire.
  • It runs in one process; the locking guarantees do not extend across servers (see the table above for what would replace them).
