Order service on AWS

The order service rebuilt for AWS: Lambda behind API Gateway, with every rule enforced by DynamoDB's conditional writes and transactions.

  • Systems (Java)
  • 2026
  • 18 tests

What it is

order-service keeps its guarantees with locks inside one process. Serverless means many short-lived Lambda instances, so the locks have to move into the database. This version keeps the same API and the same guarantees, enforced by DynamoDB instead.

It has no dependencies, like the original: no AWS SDK. It signs AWS requests itself (Signature Version 4) and talks to DynamoDB’s JSON API over HTTPS. The Lambda package is about 45 KB.

An order and its history share a partition key, so the history is one Query.

Design decisions

  • Retries that cannot double-apply. Network errors and throttling are retried with exponential backoff and jitter, using the same ClientRequestToken: if the first attempt committed and only its answer was lost, DynamoDB will not apply it again.
  • Reading why a transaction was cancelled. DynamoDB returns a reason per item. The idempotency key is checked first (another request won: replay its answer), then the order’s version (someone changed it: re-read), and only then the stock (really out of stock).
  • Expired keys count as absent. DynamoDB’s TTL deletes items in the background, sometimes days late, so the condition is attribute_not_exists(PK) OR expiresAt <= :now.
  • Least privilege. The function’s role can only read and write this one table.
  • No SDK. The SigV4 signer is tested on vectors produced by botocore, AWS’s own implementation, including the worked example in AWS’s documentation.

Tests, and what they found

18 tests run against moto, an emulator of the DynamoDB API, so they exercise the real wire protocol, the signing, condition expressions and cancellation reasons. I planted 6 bugs (the stock condition dropped, the price condition dropped, no version check, an expired key still blocking, errors not stored under their key, stock failures read before the version check). All 6 are caught.

Two bugs the tests found while I wrote it: a ship-and-cancel race was reported as data corruption because the stock failure was read before the version failure, and an HTML 500 page was parsed as JSON instead of being retried.

One finding about the emulator itself: moto does not isolate concurrent transactions, so under parallel requests it oversold. Real DynamoDB guarantees serializable transactions, so the tests run moto one request at a time; the clients still race exactly as they would against AWS.
