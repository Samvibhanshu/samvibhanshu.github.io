Route planner

Part 1: one route

Shortest-path algorithms
AlgorithmIdeaUse when
BFSExplore level by level; the first time you see a node is the fewest roads to itEvery road costs the same
DijkstraAlways finalise the closest unfinished node, using a priority queueCosts differ and are non-negative
A*Dijkstra ordered by cost so far plus an under-estimate of cost to go, so it heads for the targetYou can cheaply under-estimate the remaining cost
Bidirectional DijkstraSearch from both ends and stop when they provably cannot improveNo geometry, but roads can be followed backwards

Measured on a 200 × 200 city (40,000 junctions, 102,282 roads, 20% of junctions blocked, road costs 10–30) over 300 random routes. All three always returned the same cost. Work is counted in nodes settled, which does not depend on the machine:

Measured work per route
Nodes settled per routeTime per route
Dijkstra15,7534.3 ms
A* (Manhattan heuristic)7,263 (2.2× fewer)4.0 ms
Bidirectional10,346 (1.5× fewer)4.0 ms
  • A* explores half as much but is barely faster in wall-clock time. Each step costs more (the heuristic, more queue entries per settled node). Fewer nodes settled is not automatically less time.
  • A* is only as good as its heuristic. Roads cost 10–30, but the heuristic has to assume the cheapest to stay safe, so it under-estimates by about half on average.

The two traps, and how the code avoids them

  1. An A* heuristic that over-estimates returns wrong routes. So the cost per unit of distance is measured from the graph (the minimum over all roads of cost ÷ distance covered), not assumed. A test shows that assuming 40 per block on a city whose roads cost 5–40 does return worse routes, and another checks the measured heuristic never over-estimates and is consistent on every road.
  2. Bidirectional search must not stop at the first meeting node. The first node reached by both searches is often not on the best route. The search keeps the best total seen through any node reached from both sides, and stops only when the two frontiers’ smallest costs add up to at least that total. A 5-node test graph shows stopping early returns 10 instead of 9.

Part 2: a delivery round

Start at the depot, visit every stop once and return. That is the travelling salesman problem, which is NP-hard.

Round-planning methods
MethodCostResult
Held–Karp (dynamic programming over subsets)O(2k · k²)Optimal
Nearest neighbourO(k²)Fast, often noticeably worse
Nearest neighbour + 2-optrepeat until no improvementNever worse than its input; no guarantee of optimal

Trying every order is k!: 1.3 trillion at 15 stops. Held–Karp at 15 stops is about 7 million steps. Measured with real road costs, 40 random rounds each:

Round quality and time
StopsNearest neighbour above optimal+ 2-opt above optimal2-opt found the optimumHeld–Karp time
89.2%0.4%34 / 400.17 ms
1212.7%1.2%24 / 402.0 ms
1513.1%1.5%20 / 4021 ms

Held–Karp’s time grows about 10× from 12 to 15 stops, as 2k · k² predicts, so the planner uses it up to 16 stops and switches to nearest neighbour plus 2-opt beyond that. Costs may be one-way, so 2-opt re-costs the whole tour for each candidate move. Stops that cannot be reached raise an error naming them instead of being silently skipped.

Tests

Test classes
Test classWhat it checks
ShortestPathTestsDijkstra, A* and bidirectional match Floyd–Warshall (a different, O(n³) algorithm) on 1,500 random graphs with parallel roads, self-loops, zero-cost and closed roads, and unreachable parts. Every returned path is checked to exist and to cost what it claims. Also a 90,000-node route whose cost overflows int
AStarTestsSame cost as Dijkstra on 600 grid routes while settling under two-thirds as many nodes; the heuristic is admissible and consistent; an over-estimating heuristic really does return worse routes
DeliveryPlannerTestsHeld–Karp equals trying every permutation (400 random asymmetric matrices, up to 7 stops). 2-opt never worsens a tour and never beats the optimum. A 4-house example where greedy is provably worse (14 vs 12)

Do the tests catch real bugs? I planted 11 bugs one at a time, among them stopping bidirectional search at the first meeting, A* ignoring closed roads, a heuristic using the maximum instead of the minimum cost per unit, Held–Karp forgetting the drive back to the depot, and unreachable stops passing silently. 9 were caught. The other 2 behave identically to the original, so no test can fail them: letting BFS update a node it has already seen changes nothing, because BFS never finds a shorter way to a node later.
